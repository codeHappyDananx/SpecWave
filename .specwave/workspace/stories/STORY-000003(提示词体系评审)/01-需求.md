# 评审任务：SpecWave 提示词体系闭环检查

> 状态：待评审
> 目标：以新接触者视角，检查提示词体系是否环环相扣

## 评审背景

SpecWave 提示词体系刚完成重构，需要一个新会话以"第一次接触这套规范"的视角，检查整个体系是否能让 AI 正确遵循流程。

## 评审范围

请依次阅读以下文件，检查它们之间的引用关系和逻辑闭环：

1. `.specwave/settings.json` - 会话锁定配置
2. `AGENTS.md` - 协作说明（入口）
3. `.specwave/roles/需求分析师.md` - 需求分析师角色
4. `.specwave/roles/开发执行者.md` - 开发执行者角色
5. `.specwave/templates/01-需求.md` - 需求模板
6. `.specwave/templates/02-设计.md` - 设计模板
7. `.specwave/templates/03-任务.md` - 任务模板

## 评审检查点

### 1. 会话锁定闭环
- [ ] AGENTS.md 是否明确要求"先读 settings.json"？
- [ ] settings.json 的 currentSession 字段定义是否清晰？
- [ ] 进入/退出 spec 模式的触发词是否明确？
- [ ] 模式切换后的行为是否有明确指引？

### 2. 阶段流转闭环
- [ ] 4 个阶段（诉求对齐→需求编写→设计方案→任务拆解）是否在所有文档中一致？
- [ ] 每个阶段的进入条件是否明确？
- [ ] 每个阶段的落盘动作是否明确？
- [ ] 阶段推进口令（"继续"/"开始"）是否一致？
- [ ] 是否有防止"抢阶段"的约束？

### 3. 落盘闭环
- [ ] 每个阶段对应的落盘文件是否明确（01-需求/02-设计/03-任务）？
- [ ] 落盘时机是否明确（阶段完成时必须落盘）？
- [ ] 落盘确认格式是否统一（✅ 已落盘：xxx）？

### 4. 角色边界闭环
- [ ] 需求分析师的"禁止改代码"是否足够强调？
- [ ] 开发执行者的"只执行任务清单"是否足够强调？
- [ ] 角色切换时机是否明确（用户说"开始"后切换）？

### 5. 表达规范闭环
- [ ] "不做问卷"的约束是否在多处强调？
- [ ] "先给方案让用户改"是否有具体示例？
- [ ] 禁止 WHEN/THEN/SHALL 是否明确？

- 重点关注：能否防止 AI 抢阶段（比如在需求编写阶段就开始写代码）
