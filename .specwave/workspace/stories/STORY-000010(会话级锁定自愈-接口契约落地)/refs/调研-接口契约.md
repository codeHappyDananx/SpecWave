# 调研：接口契约与复杂交互如何稳定落地

> 只记结论：适用点、产物长什么样、怎么回归。

## 1) 先把“契约”分清楚：两类路线

### 1.1 契约先行（Contract-first）

代表：OpenAPI / AsyncAPI / OpenRPC  
适用：接口形态稳定、团队愿意先对齐接口，再并行开发。

落地产物：
- 一份机读契约（如 `openapi.yaml`），作为单一真相源。
- 一份“中文解释版”（字段语义、失败语义、状态机与 UI 行为），给人读。
- 一套回归清单（最短路径），给 QA/自己跑。

怎么回归：
- mock server（例如 Prism 之类的 OpenAPI mock）让前端先跑起来。
- schema 校验（请求/响应对 schema）防漂移。
- 变更 diff（对比契约文件变更）提示影响面。

### 1.2 消费者驱动契约（Consumer-driven Contract）

代表：Pact  
适用：多个消费者依赖同一个提供者；希望用“交互示例”把真实约定锁死，减少脆弱的 E2E。

落地产物：
- consumer 侧写契约测试，产出 pact 文件（交互示例）。
- provider 侧验证 pact，确认兼容后再发布。

怎么回归：
- CI 里跑 provider verification + `can-i-deploy` 类检查，阻止不兼容发布。

## 2) 对我们这个痛点，推荐落地形态（最少但够用）

### 2.1 “交互契约包”= 人读 + 机读 + 回归清单

人读（必须）：
- 接口清单：接口名 + 触发 UIIntent + 成功/失败语义
- 请求/响应示例：成功/失败各 1
- 字段语义表：来源/含义/为空语义/默认值/格式/单位
- 错误码与失败语义：怎么提示、能否重试、是否回滚
- 状态机：前端控件状态 ↔ 后端业务状态
- 回归清单：成功/失败/边界最短步骤

机读（可选增强，但建议逐步引入）：
- REST：OpenAPI v3.1（契约文件可做 diff + schema 校验）
- 事件：AsyncAPI（并配合 Schema Registry）
- JSON-RPC：OpenRPC

## 4) 给 SpecWave skills 的改造要点（结论）

1) 不只拆任务：必须把“接口口径 + 状态机 + 失败语义”落成契约包，并让任务强制引用。  
2) 契约优先级高于“口头约定”：执行阶段发现契约缺失/冲突，要暂停回需求补齐。  
3) 逐步引入机读契约：先把人读版写扎实，再上 OpenAPI/AsyncAPI/OpenRPC 与自动校验。
