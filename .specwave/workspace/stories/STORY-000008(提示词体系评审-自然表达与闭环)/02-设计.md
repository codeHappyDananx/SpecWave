# 设计方案

> Story：STORY-000008(提示词体系评审-自然表达与闭环)
> 状态：编写中

## 架构概述

这次改造只做两件事：

1) **流程更稳**：会话锁定优先、门禁更硬、口径一致（四阶段 + 三文档）。  
2) **表达更自然**：不靠口号和固定数字约束，而是靠“下一步怎么做 + 怎么验”的写法，让新人也能跟着走。

借鉴 ZCF workflow 的关键点（用到 SpecWave 的语境里）：

- 把“流程”和“表达”拆开：流程负责什么时候做什么；表达负责把事情讲清楚。
- 每一步都要有产物与可验证的结果：落盘到工作区、或跑一次 create 输出证据。
- 每一步结束都告诉用户怎么推进：继续/开始，避免用户猜规则。

| `specwave-skills/resources/packs/core/light` | 规范源：`.specwave` 的 roles/prompts/templates/settings | 只改这里，不手改生成产物 |

## 关键设计点

### A. 移除“提示词痕迹”

- 删除/替换自我标注式口号。
- 删除“固定行数/固定提问数量”类硬约束，改成：
  - 默认短、默认直给；
  - 信息不够再问，并说明“为什么必须问这个”；
  - 问完就推进，不做问卷。

### B. 口径只认一套

- 四阶段：诉求对齐 → 需求编写 → 设计方案 → 任务拆解 →（开始）执行
- 三文档：`01-需求.md` / `02-设计.md` / `03-任务.md`
- 门禁：需求阶段只落盘工作区；执行阶段才允许改代码/跑副作用命令，且必须拿到“开始”。

### C. create 自检兜底

把“容易回滚成旧口径”的内容变成 plan 阶段就能失败的检查项，例如：

- 禁止词（如：WHEN/THEN/SHALL）与自我标注式口号。
- 阶段名顺序与三文档命名一致性。
- `currentSession` 保留策略（create 不得清空正在进行的会话）。

## 风险与依赖

- 风险：用户没设置 `CODEX_HOME` 时，create 会写到全局环境，导致误以为“本项目没更新”。  
  - 应对：create 的 plan 输出明确提示当前 `CODEX_HOME` 指向哪里，并给出“只影响本项目”的做法。
- 风险：历史 story/文档中可能残留旧写法，影响搜索与理解。  
  - 应对：清理可见的旧写法，归档内容也做最小清理，避免污染全局检索。
