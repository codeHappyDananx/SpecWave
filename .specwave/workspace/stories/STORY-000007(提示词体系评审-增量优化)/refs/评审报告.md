# 评审报告

> Story：STORY-000007(提示词体系评审-增量优化)
> 状态：已评审

## 评审结论

- 结论：当前“进入 spec 后绝对服从”有口径漂移风险，主要来自项目内 `.codex` 的旧 `specwave-router` 与 `.specwave`/pack 的规范不一致，容易导致抢跑、说话抽象、以及文档口径互相打架。
- 建议：先做最小增量修复包（会话锁定优先 + 清理废话句式 + 清掉 EARS 旧口径 + create 明确 `CODEX_HOME` 影响范围），再跑 `specwave create --plan` 做一致性回归。

## 问题清单

### P0-001 路由规则忽略“会话锁定”，会把 spec 跑回 vibe

- 证据：`AGENTS.md:5` 明确“会话锁定必须执行”；但 `specwave-skills/resources/codex/skills/specwave-router/SKILL.md:13` 仍写“vibe 默认直接干活”。
- 风险：`currentSession.mode=spec` 时，用户一句“帮我改一下”可能被路由成 vibe，出现抢跑/不按 phase。
- 建议改动点：在 router skill 顶部加最高优先级规则：先读 `.specwave/settings.json`，只要 `currentSession.mode=spec` 就强制按 spec 当前阶段继续。
- 验证方式：把 `.specwave/settings.json` 的 `currentSession.mode` 设为 `spec` 后，输入“帮我改一下”，回复仍以 `【spec 模式 - <阶段>】` 开头且不直接开工。

### P0-002 项目内 `.codex` 的 router skill 与内置资源不一致（用户会误判“create 没覆盖旧的”）

- 证据：项目内 `​.codex/skills/specwave-router/SKILL.md:56` 仍写“EARS 格式”；而内置资源 `specwave-skills/resources/codex/skills/specwave-router/SKILL.md` 根本没这段。
- 风险：同一个仓库里出现两套不同“规范源”，实际对话按哪套走变得不可预测；用户体感就是“提示词没刷新”。
- 建议改动点：统一以 `specwave-skills/resources/codex/skills/specwave-router/SKILL.md` 为真相源，并让项目 `.codex` 由 create（通过 `CODEX_HOME` 指向项目）覆盖更新。
- 验证方式：设置 `CODEX_HOME` 指向项目 `.codex` 后运行 create，确认 `.codex/skills/specwave-router/SKILL.md` 内容与资源一致。

### P1-003 “EARS”旧口径在两处出现，和当前模板/规则打架

- 证据：项目 skill `​.codex/skills/specwave-router/SKILL.md:56` 写“EARS 格式”；对外说明 `specwave-skills/README.md:47` 也写“EARS 格式需求”。
- 风险：读文档的人会按 EARS 写 WHEN/THEN，直接撞上“禁止 WHEN/THEN/SHALL”的硬规则，导致需求文档风格反复横跳。
- 建议改动点：把所有“EARS”描述替换为“操作/预期 + AC（操作 → 预期）”；以模板 `specwave-skills/resources/packs/core/light/.specwave/templates/01-需求.md` 为准。
- 验证方式：`rg -n "EARS 格式"` 在仓库内无结果；新写需求只出现“操作/预期/验收口径”。

### P1-004 skill 引导的句式会诱发废话，且与协作规则冲突

- 证据：`​.codex/skills/specwave-router/SKILL.md:13` 要求“先复述你理解的点”；而 `AGENTS.md:59` 明确要求不要说“我理解你的意思是...”。
- 风险：对话会出现“先复述一遍 + 再问一次”的重复废话，用户体感就是“抽象、绕、像在背提示词”。
- 建议改动点：把“复述理解”改成一句直给的行动描述：
  - 推荐句式："我会先做 A，然后把 B 写进文档；你只要确认 C 对不对？"
- 验证方式：触发 spec 的首轮回复不出现“我理解…”句式，且最多只问 1 个关键问题。

### P1-005 “落盘不算执行”写法容易让用户觉得抢跑

- 证据：`​.codex/skills/specwave-router/SKILL.md:14` 写“工作区文档落盘不算执行，可直接做”。
- 风险：从用户视角看，写文件本身就是副作用；如果没有提前说清“我要写哪些文件”，容易被认为是抢跑。
- 建议改动点：把规则改成“需求阶段会落盘文档（并提前告知写哪些）；改代码/跑命令必须等开始”。
- 验证方式：每次写入工作区文档前，回复里明确点名要写的文件（如 `01-需求.md`），并说明这是需求阶段动作。

### P1-006 `specwave create` 默认改全局 `CODEX_HOME`，需要更显眼的提示

- 证据：`specwave-skills/bin/specwave.js:2348` 默认 `CODEX_HOME` 为用户目录；且 `specwave-skills/bin/specwave.js:1822` 会“启用 Codex 全局资源”。
- 风险：用户以为只刷新当前项目，实际把全局 Codex 行为也改了；一旦别的项目用同一套 Codex，就会被连带影响。
- 建议改动点：
  - README 补一句：要只影响项目，把 `CODEX_HOME` 指到项目 `.codex`。
  - create 的 plan 输出里加一条显眼提示：当前 `CODEX_HOME` 指向哪里，会写哪些全局文件。
- 验证方式：运行 `create --plan` 能看到 `CODEX_HOME` 路径与“只影响项目”的一行指引。

### P1-007 “多处维护同一规则”是长期漂移源，需要自检兜底

- 证据：会话锁定在 `AGENTS.md:5`，路由规则在 `specwave-skills/resources/codex/skills/specwave-router/SKILL.md:13`，对话细则又在 `​.codex/skills/specwave-router/SKILL.md:25`。
- 风险：只要有一处没更新，就会出现“同一件事在不同文件里说法不一样”，最终变成不可控屎山。
- 建议改动点：在 `specwave create --plan` 阶段做一致性自检：阶段名顺序、三文档命名、禁用关键词（WHEN/THEN/SHALL）必须一致；发现冲突直接报错。
- 验证方式：制造一个冲突（比如把某处写成 `02-任务.md`）时，create 在 plan 阶段就 fail fast。

### P1-008 内置 router skill 太短，缺少“怎么说人话”的默认口径

- 证据：`specwave-skills/resources/codex/skills/specwave-router/SKILL.md:40` 只有“不理解就先确认/执行要等开始”等抽象底线。
- 风险：模型会用自己的默认表达兜底，容易回到“术语堆叠/抽象总结/问卷式确认”。
- 建议改动点：给 router skill 加一条很短的“默认输出模板”（3~6 行）：先说你要做什么，再说你需要用户回什么；术语同句解释。
- 验证方式：触发 spec 的首轮回复稳定保持“短 + 可操作”，而不是大段流程复述。

### P0-003 `specwave create` 合并 settings 会清空 `currentSession`（会话锁定断掉）

- 证据：模板 `specwave-skills/resources/packs/core/light/.specwave/settings.json:5` 把 `currentSession` 设为 `null`；如果 merge 直接用模板覆盖，就会把正在进行的 spec 会话清掉。
- 风险：用户在 spec 里跑一次 create，会话直接变回“无会话”，下一轮对话可能按 vibe 走，出现抢跑/丢进度。
- 建议改动点：`specwave-skills/bin/specwave.js:1272` 起，对 `currentSession` 做保留策略：如果现有值非空，create/refresh 不覆盖。
- 验证方式：先把 `.specwave/settings.json` 写成 `currentSession.mode=spec`，再跑 `create --agree`，确认 `.specwave/settings.json` 里的 `currentSession` 仍存在。
