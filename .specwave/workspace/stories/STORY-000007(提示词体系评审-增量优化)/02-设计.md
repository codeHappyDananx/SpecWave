# 设计方案

> Story：STORY-000007(提示词体系评审-增量优化)
> 状态：编写中

## 架构概述

用“会话锁定 + 口径统一 + 可验证表达”三件事，把提示词工程做成可重复刷新、不会抢跑、也不会把人绕晕的一套协作系统。

核心做法：
- 进入 spec 后，一律以 `.specwave/settings.json` 的 `currentSession` 为准（会话锁定优先级最高）。
- 用同一套“阶段名 + 三文档（01/02/03）”做唯一口径，并让 `specwave create` 刷新后清理旧口径残影。
- 把对话输出的默认写法改成“结果 + 怎么验”，不再用抽象词当结论；术语出现就顺手解释。

## 组件职责

| 组件 | 职责 | 边界 |
|------|------|------|
| `specwave-skills/resources/packs/core/light` | 规范真相源：roles/prompts/templates/settings | 只改这里，不手改生成产物 |
| `specwave-skills/resources/codex/skills/specwave-router` | Codex 路由技能真相源 | 由 `specwave create` 安装到 `CODEX_HOME` |
| `specwave-skills/bin/specwave.js` | `specwave create`：生成计划、刷新 `.specwave`、清理旧文件、安装 Codex 资源 | 只做受控覆盖/合并/清理 |
| 项目 `.specwave/*` | 运行时规范与工作区 | 不是规范源，允许被刷新 |
| 项目 `.codex/*` | （可选）项目内 Codex 资源 | 只在 `CODEX_HOME` 指向项目时写入 |
| `.specwave/workspace/*` | Story/验收/证据工作区 | 只落“决定”，不写过程复盘 |

## 数据模型

无新增业务数据结构。本 Story 的“数据”只有两类：
- 规范文件（roles/prompts/templates/settings/skills）
- 证据文件（`refs/` 下的评审报告、create 输出、对比结果）

## 关键技术决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 会话锁定优先级 | 先看 `.specwave/settings.json`，有 spec 会话就强制按阶段继续 | 防止路由被用户一句话带偏，避免“抢跑/跑回 vibe” |
| 表达默认写法 | “结果 + 怎么验”，术语同句解释 | 新人能读懂，评审能直接验收 |
| `.codex` 覆盖策略 | 支持用 `CODEX_HOME` 指向项目 `.codex` 来做项目内安装 | 避免误改全局环境，同时解决“本项目仍在用旧 skill”的问题 |
| 一致性校验 | 在 `specwave create --plan` 阶段做轻量自检（发现口径冲突就 fail fast） | 把“口径不一致”提前变成明确错误，而不是靠人肉发现 |

## 风险与依赖

- 风险：用户未设置 `CODEX_HOME` 时，create 会写到全局 `~/.codex`；需要在文档与 `refs/` 里明确“如何只影响项目”。
- 风险：历史遗留的项目内 `.codex/skills/specwave-router` 可能与 pack 不一致；需通过本次刷新把口径统一。
- 依赖：本 Story 所有改动以 `specwave-skills/resources/*` 为准，最终用 `specwave create --plan`/落盘验证一致性。
