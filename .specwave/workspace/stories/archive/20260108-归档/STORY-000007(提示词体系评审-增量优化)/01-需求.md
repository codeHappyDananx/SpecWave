# 需求文档

> Story：STORY-000007(提示词体系评审-增量优化)
> 状态：编写中

## 概述

把 SpecWave 的“进入 spec 后的行为”调得更好理解、更不抢跑：不懂术语也能按提示一步步走；只要会话处于 spec，就严格按流程推进；把容易误导人的抽象话清掉，用可验证的结果说话。

## 你最终会看到什么

- 你触发 spec（新建需求/开 story/走流程）后，我第一行固定 `【spec 模式 - 诉求对齐】`，并直接说清：我接下来要做什么、你要回什么。
- 只要 `.specwave/settings.json` 里 `currentSession.mode` 是 `spec`，我就不会跑回 vibe；你让我“直接改代码”，我也会先把任务拆进 `03-任务.md`。
- 我不会拿“闭环/一致性/赋能/落地”当结论；每个结论都能被你立刻验证（你按我说的操作，就能看到预期结果）。
- 运行 `specwave create --plan` 能看到：`.specwave` 与（项目内或全局）`.codex` 的关键文件口径一致，不会出现“阶段名/文件名互相矛盾”。

## 需求清单

### REQ-001 会话锁定优先（不被一句话带偏）

- **操作**：当 `.specwave/settings.json` 存在，且 `currentSession.mode` 为 `spec` 时，你输入“帮我改一下/加个功能/直接实现”。
- **预期**：我仍按 spec 当前阶段输出（标题 `【spec 模式 - <阶段>】`），不会直接开工改代码，也不会把对话切回 vibe。

### REQ-002 首轮输出要短、可操作

- **操作**：你触发“新建需求/开 story/走流程”进入 spec。
- **预期**：我用短段落说清楚：我准备做什么、我需要你确认哪一句、你下一步回“继续”还是“开始”；信息不够时，只补问推动下一步必须的点，并说明原因。

### REQ-003 术语出现就顺手解释（不默认你懂）

- **操作**：在需求/设计/任务任何阶段，我提到 `UIIntent` / `ViewModel` / `store` / `preload` / `IPC` 等词。
- **预期**：我会在同一句话里把它翻成你能听懂的意思，并结合当前项目顺手举例；不会只丢术语当结论。

### REQ-004 口径统一（阶段名 + 三文档命名）

- **操作**：你让流程推进（连续回复“继续”，或直接要求我“下一步是什么”）。
- **预期**：我只按这个顺序推进：诉求对齐 → 需求编写 → 设计方案 → 任务拆解；并且只使用 `01-需求.md` / `02-设计.md` / `03-任务.md` 这套命名。

### REQ-005 `specwave create` 刷新后不留旧口径残影

- **操作**：你运行 `specwave create --plan`（或实际落盘刷新）。
- **预期**：旧的 prompts/roles（官方托管部分）会被覆盖/清理；不会出现“同一件事在不同文件里写法不一样”的情况。

### REQ-006 评审要可落地（不写空话）

- **操作**：你让我做提示词/skills/CLI 的评审。
- **预期**：`refs/评审报告.md` 列出主要问题清单；每条都写清：哪里写得抽象 → 改成更直白的说法 → 怎么验证，并引用到 `文件名:行号`。

## 验收口径

- **AC-001**：你说“新建需求”，回复第一行是 `【spec 模式 - 诉求对齐】`。
- **AC-002**：在 spec 会话里，你说“直接改代码”，我不会执行改动；会先指向 `03-任务.md` 并说清“现在缺哪一步、你该回什么”。
- **AC-003**：在对话里出现 `UIIntent` / `ViewModel` 等词时，同一句话里带中文解释 + 项目内例子。
- **AC-004**：运行 `node specwave-skills/bin/specwave.js create --plan`，看不到“阶段名/文件名矛盾”的内容。
- **AC-005**：`refs/评审报告.md` 覆盖主要问题，且每条包含“改动点 + 验证方式 + 文件名:行号”。

## 边界约束（给实现用）

- 本 Story 只改“规范与工具”：`specwave-skills/`、项目 `.specwave/`、项目 `.codex/`、工作区文档；不改业务功能代码。
- 改动涉及职责/入口/边界时，同步合并更新 `.specwave/workspace/project-map.md`。
