# 设计方案

> Story：STORY-000013(store.ts 拆分-按意图域拆处理器)  
> 状态：编写中

## 架构概述

保持 `dispatch(intent)` 的唯一入口不变，把 `apps/desktop/src/renderer/src/store.ts` 里按 `UIIntent.type` 的巨型 `switch` 拆成“按意图域分文件”的 handler 模块；每个模块只处理自己域的 intent，并把该域相关的辅助函数一并搬过去，最终让 `store.ts` 只剩 store 初始化 + dispatch 编排 + 少量通用 glue（胶水）。

## 组件职责

| 组件 | 职责 | 边界 |
|------|------|------|
| `apps/desktop/src/renderer/src/store.ts` | store 入口：`useAppStore` 创建、`intentLog` 记录、dispatch 编排（分发到各 handler）、对外导出 | 不再承载各域业务细节；不直接堆所有 case |
| `apps/desktop/src/renderer/src/store/dispatch.ts` | `dispatch` 的路由层：根据 `intent.type` 把 intent 交给对应域 handler；提供统一的 handler 上下文（`set/get`） | 不做业务；只做路由与兜底 |
| `apps/desktop/src/renderer/src/store/handlers/panel.ts` | 面板与视图：`PANEL_*`、`RIGHT_MODE_SET`、`LEFT_VIEW_MODE_SET`、`RIGHT_PANEL_ADD` | 只负责可见性、模式切换、布局归一化，不碰文件/任务域 |
| `apps/desktop/src/renderer/src/store/handlers/story.ts` | Story 看板与阶段：`STORY_*`、`PHASE_INDICATOR_CLICK`、`STORY_STEPPER_PHASE_CLICK` | 只负责 stories 目录读取、卡片构建、阶段跳转（通过 dispatch EXPLORER_OPEN_FILE） |
| `apps/desktop/src/renderer/src/store/handlers/project.ts` | 项目与 tabs：`PROJECT_*`、`RECENT_PROJECT_REMOVE`、`GLOBAL_SEARCH_SET` | 只负责项目打开/切换/关闭、会话持久化（sessionStorage） |
| `apps/desktop/src/renderer/src/store/handlers/explorer.ts` | 文件树：`EXPLORER_*` | 只负责树节点展开/收起、打开文件、在 OS 定位 |
| `apps/desktop/src/renderer/src/store/handlers/content.ts` | 内容区：`CONTENT_*` | 只负责编辑/保存/查找（find）与内容模式切换 |
| `apps/desktop/src/renderer/src/store/handlers/task.ts` | 任务板：`TASK_*` | 只负责任务勾选、详情、deck 切换、关联文档跳转等 |

| `apps/desktop/src/renderer/src/store/handlers/chat.ts` | 对话：`CHAT_*` | 只负责会话切换、草稿、消息提交 |

## 数据模型

```ts
// 目标：把 handler 的签名统一，方便分文件、单测与逐域验证。
type StoreCtx = {
  set: (updater: (s: AppState) => Partial<AppState> | void) => void;
  get: () => AppState;
  // 允许 handler 触发派发（用来做 queueMicrotask 内的跳转）
  dispatch: (intent: UIIntent) => void;
};

type HandlerResult = Partial<AppState> | void;

// 每个域 handler 只处理自己域的 intent；外层 dispatch 负责路由。
type DomainHandler<T extends UIIntent["type"]> = (args: {
  ctx: StoreCtx;
  state: AppState;
  intent: Extract<UIIntent, { type: T }>;
}) => HandlerResult;
```

> 备注：实际实现时可不暴露全部类型，只要保证“handler 只关心 state/vm 与副作用，返回局部 state patch”即可。

## 关键技术决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 意图域怎么划分 | 按 `UIIntent.type` 前缀分域（PANEL/PROJECT/EXPLORER/CONTENT/TASK/TERMINAL/CHAT/LAYOUT/SHORTCUT/THEME/STORY） | 与 contracts 类型天然一致，边界清晰，新增 intent 时容易找到落点 |
| handler 如何落地 | “搬 case 代码”为主，逻辑不重写 | 以最小改动保证行为不变，降低引入新 bug 的概率 |
| 异步副作用放哪 | 保持在原 case 内（搬到 handler 后仍然在 handler 内） | 不改变时序；依旧用 `window.specwave` 与 `set` 回写 |
| 如何避免循环依赖 | domain 相关 helper 跟随 handler 搬到同文件/同域模块；通用 helper 放 `store/shared/*` | 避免 `store.ts ↔ handler` 互相 import 导致循环 |
| 逐步验证策略 | “一个域一条任务”，每条任务做类型检查 + 该域关键交互冒烟 | 发现问题可快速定位回滚，符合 REQ-004 |

本次属于前端 store 的内部重构，不新增接口契约。

## 风险与依赖

- 风险：case 合并/fallthrough（例如 `case A:` + `case B:` 共用一段）在拆分时容易被误改；需要按域提取时保留原结构。
- 风险：handler 内部使用 `set/get/dispatch` 的闭包引用，拆分后若签名不统一会导致可读性变差；需要统一 `StoreCtx`。
- 依赖：`zustand` 的 `set((state) => patch)` 语义保持不变；拆分中禁止把“同步 patch”改成“异步 set”，避免时序变化。
