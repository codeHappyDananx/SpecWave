# 需求文档

> Story：STORY-000008(提示词体系评审-自然表达与闭环)
> 状态：编写中

## 概述

对 SpecWave 这套“提示词工程 + 工作区落盘 + create 刷新”做一次增量评审与修整，目标是：

- 只要进入 spec，会话锁定就永远优先，不被用户一句话带偏，不会抢跑。
- 输出更自然、更直给：不写自我标注，不堆抽象词，不用硬性数字规则吓人。
- 口径只认一套：四阶段名称、三文档命名、门禁触发条件在所有文件里一致。
- 评审结果可验证：你照着操作就能看到结果，而不是“感觉更好了”。

## 你最终会看到什么

- 你触发 spec（新建需求/开 story/走流程）后，我第一行就是 `【spec 模式 - 诉求对齐】`，紧跟着把“我马上要做什么 / 你怎么推进（继续/开始）”说清楚。
- 只要 `.specwave/settings.json` 里 `currentSession.mode` 是 `spec`，我就不会回到 vibe；你让我“直接改代码”，我也会先把事情拆进 `03-任务.md`，等你确认再动手。
- 我说结论时会带验证方式：你怎么操作、应该看到什么，一眼能判对错。
- 你跑 `specwave create` 时能看懂它在做什么：先给计划（只展示）、再落盘刷新（真的写入），并且不会把旧口径残留在项目里。

## 需求清单

### REQ-001 会话锁定优先（进入 spec 后不跑偏）

- **操作**：当 `.specwave/settings.json` 存在，且 `currentSession.mode` 为 `spec` 时，你输入“帮我改一下/加个功能/直接实现”。
- **预期**：我仍按 spec 当前阶段输出（标题 `【spec 模式 - <阶段>】`），不会直接开工改代码，也不会把对话切回 vibe。

### REQ-002 首轮输出要短、可操作（不背流程）

- **操作**：你触发“新建需求/开 story/走流程”进入 spec。
- **预期**：我会把三件事说清楚：我接下来要做什么、我会写哪些文档、你下一步该回什么（继续/开始）。信息不够时，只补问推动下一步必须的点，并说明我为什么需要它。

### REQ-003 术语随用随解释（不默认你懂）

- **操作**：在需求/设计/任务任何阶段，我提到 `UIIntent` / `ViewModel` / `store` / `preload` / `IPC` 等词。
- **预期**：我会在同一句话里给出简短解释，并结合当前项目顺手举例；不会只丢术语当结论。

### REQ-004 口径统一（四阶段 + 三文档）

- **操作**：你让流程推进（回复“继续”，或直接问我“下一步是什么”）。
- **预期**：我只按这个顺序推进：诉求对齐 → 需求编写 → 设计方案 → 任务拆解；并且只使用 `01-需求.md` / `02-设计.md` / `03-任务.md` 这套命名。

### REQ-005 `specwave create` 刷新后不留旧口径残影

- **操作**：你运行 `specwave create --plan` 查看计划，再运行落盘刷新（例如 `--agree`）。
- **预期**：对话与落盘所依赖的 prompts/roles/skills 以资源包为准被覆盖更新；不会出现“同一规则在不同文件里写法不一样”的情况；并且不会清空正在进行的 `currentSession`。

### REQ-006 门禁表达要符合用户视角（避免被认为抢跑）

- **操作**：在 spec 的需求阶段，我需要落盘工作区文档；在执行阶段，我需要改代码或运行带副作用的命令。
- **预期**：需求阶段写文档前，我会提前点名要写哪些文件；改代码/跑命令前，我会明确说明要做什么，并等待你说“开始”。

### REQ-007 评审输出可落地（能直接指导改）

- **操作**：你让我对提示词/skills/CLI 做评审。
- **预期**：我会在 `refs/评审报告.md` 里写清：哪里让人读不懂或容易跑偏 → 建议改成什么写法 → 怎么验证；并引用到 `文件名:行号`，方便你快速定位与复核。

## 验收口径

- **AC-001**：你说“新建需求”，回复第一行是 `【spec 模式 - 诉求对齐】`，并明确你下一步回“继续”还是“开始”。
- **AC-002**：在 spec 会话里，你说“直接改代码”，我不会执行改动；会先把任务拆进 `03-任务.md`，并说明当前缺哪一步。
- **AC-003**：对话与相关文档里不出现自我标注式口号；也不使用“固定行数/固定提问数量”这类硬规则当结论。
- **AC-004**：用项目内 `CODEX_HOME` 运行 `specwave create --plan/--agree` 后，`.specwave` 与 `.codex` 的关键口径一致，且 `currentSession` 不被清空。
  - 证据文件落在 `refs/`（create 输出、对比结果）。
- **AC-005**：`refs/评审报告.md` 的问题与改法能直接指导后续改动，并且每条都有“怎么验证”的操作口径。

## 边界约束（给实现用）

- 本 Story 只改“规范与工具”：`specwave-skills/`、项目 `.specwave/`、项目 `.codex/`、工作区文档；不改业务功能代码。
- 改动涉及职责/入口/边界时，同步合并更新 `.specwave/workspace/project-map.md`。
