# 设计方案

> Story：STORY-000010(会话级锁定自愈-接口契约落地)  
> 状态：编写中

## 架构概述

核心思路：把 `.specwave/settings.json` 里的“会话状态”从“全局单例”改成“按会话分桶”，同时保留一个可兼容的 `currentSession` 投影；用一个轻量脚本在对话开始时把投影对齐到当前会话，解决多会话串线。

## 组件职责

| 组件 | 职责 | 边界 |
|------|------|------|
| `session_guard.py` | 识别当前 Codex 会话 ID；读写 `.specwave/settings.json`；维护会话分桶与 `currentSession` 投影 | 不参与业务需求内容生成，只负责“状态读写与自愈” |
| `specwave-router` skill | 在任何路由判断前提醒/要求执行 `sync`；并在复杂对接场景强制“交互契约包”落盘 | 不替代需求分析师/开发执行者，只做门禁与路由提示 |
| “交互契约包”（工作区产物） | 把接口口径、字段语义、错误码、状态机、回归用例固定落盘 | 只存“决定”，不写讨论过程 |

## 数据模型（settings.json 扩展）

保留现有字段不破坏兼容，并新增会话分桶存储：

- `sessionStore.version`：整数版本号（便于未来迁移）。
- `sessionStore.bySessionId.{sessionId}`：每个会话一个桶，桶里保存该会话的 `currentSession` 等必要信息。
- `currentSession`：只作为“当前会话投影”，由 `session_guard.py sync` 写入；不再作为全局真相源。
- `sessionStore.legacy`：可选，用于收容旧结构迁移记录（方便排查但不参与路由）。

## 会话 ID 识别策略

目标：在无法从模型侧直接拿到“当前会话 ID”的前提下，尽量从本机可观测信息稳定识别。

- 数据源：`~/.codex/sessions/**/rollout-*.jsonl` 首行 `type=session_meta` 的 `payload.id` 与 `payload.cwd`。
- 过滤：只匹配 `payload.cwd == 项目根路径` 的 rollout。
- 选择：按 rollout 文件的最后更新时间排序取最新。
- 并发保护：若多个候选在很短时间内都活跃（例如 3 秒内），拒绝自动选择，要求显式 `--session-id`。

## 会话守卫脚本设计

命令（示例）：

- `python .../session_guard.py status`：输出当前会话 ID、当前投影与分桶状态（只读）。
- `python .../session_guard.py sync`：把 `sessionStore.bySessionId` 与 `currentSession` 对齐到当前会话（必要时迁移旧结构）。
- `python .../session_guard.py set --mode spec --story STORY-000010 --phase 诉求对齐`：只更新当前会话桶，并同步投影。
- `python .../session_guard.py clear`：清空当前会话桶与投影（退出 spec）。

写入策略：只改 `.specwave/settings.json`；其它文件不动，避免扩大影响面。

## 交互契约包（Contract Pack）设计

适用触发：需求涉及任一项就必须产出契约包，并在任务中引用：

- 前端控件与后端接口对接（表单校验、分页、筛选、导入导出、按钮权限等）。
- 跨进程/跨服务调用（IPC/RPC/HTTP/MQ）。
- 存在状态机/模式切换（加载中、重试、幂等、部分成功、降级）。

建议落盘位置：`Story/refs/contracts/`（只放决定，方便跨会话复用）。

契约包内容（最小集）：

1) **接口清单**：接口名 + 路径/方法 + 触发时机（哪个 UIIntent/哪个按钮）。  
2) **请求/响应示例**：用最小可跑通的 JSON 示例描述成功与失败各 1 份。  
3) **字段语义**：每个关键字段说明来源、含义、为空语义、默认值、单位与格式。  
4) **错误码与失败语义**：错误如何展示、是否可重试、是否需要回滚、返回空还是报错。  
5) **状态机**：前端控件状态（禁用/loading/成功/失败/部分成功）与后端业务状态如何对应。  
6) **回归清单**：成功/失败/边界路径各 1~2 条最短操作步骤。

机读版本（可选增强）：

- HTTP/REST：OpenAPI（推荐 v3.1，便于 JSON Schema 一致表达）。
- 事件驱动：AsyncAPI（并配合 Schema Registry）。
- JSON-RPC：OpenRPC。
- 契约测试：Pact（偏“消费者驱动契约”）或基于 OpenAPI/JSON Schema 的 schema 校验。

## 关键技术决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 会话状态存储 | `settings.json` 增加 `sessionStore.bySessionId` | 改动小、兼容老逻辑、可在脚本里自愈迁移 |
| 会话 ID 来源 | rollout 首行 `session_meta.payload.id` | 比“最后一条消息”更稳定，且可用 `cwd` 过滤到项目 |
| 契约落盘方式 | `refs/contracts/` + 任务引用 | 让复杂交互“可查可复用”，跨会话实现不靠脑补 |

## 风险与依赖

- 本方案依赖本机存在 Codex 的 rollout 日志；若未来日志路径变化，需要同步调整识别逻辑。
- 若同项目同时跑多个会话且都活跃，自动绑定可能不可靠，必须靠 `--session-id` 显式指定。
