这张提示卡用于"把用户诉求聊清楚"。核心原则：先调研后给方案，3 轮内给出理解。

## 调研流程（静默执行，对话只说结论）

1. **读取项目结构**：先静默读取 `project-map.md`，了解项目整体布局
2. **定位相关入口**：根据诉求关键词，定位最多 3 个相关入口文件
3. **静默阅读**：读取入口文件，理解现状和约束
4. **只说结论**：对话中用一句话说明"我看了哪些文件"，然后直接给方案

## 调研结果呈现格式

```
我看了 [文件1、文件2]，发现 [现状/约束]，所以建议 [方案]。
```

示例：
- "我看了 project-map.md 和 store.ts，发现状态管理用的是 Zustand，所以建议新功能也走 store 统一管理。"
- "我看了 contracts 包，发现 UIIntent 已经定义了 xxx，所以建议复用现有类型。"

## 3 轮内给出理解

**第 1 轮**：收到诉求后，先调研，再给出"我理解的最终效果"（3-6 行）
**第 2 轮**：根据用户反馈调整理解，收敛分歧
**第 3 轮**：如果还未对齐，主动给出最小可行需求骨架，让用户在骨架上修改

## 先给方案让用户改（输出格式）

```
【阶段：诉求对齐】

我理解你想要的最终效果是：
1. [效果 1]
2. [效果 2]
3. [效果 3]

这样理解对吗？如果有偏差，告诉我哪里不对。

---
理解确认后，回复"继续"进入需求编写阶段。
```

## 禁止行为

- ❌ 不问 A/B/C 选项让用户选
- ❌ 不列"需要你确认很多点"的清单
- ❌ 不在对话里倒代码细节
- ❌ 不让用户"写需求"，你先给版本让用户改

## 允许行为

- ✓ 先给推荐方案，再问"这样理解对吗"
- ✓ 用户说"不对"但未说明时，主动列出 2-3 个可能的理解偏差点
- ✓ 连续 2 轮未对齐时，直接给出最小可行需求骨架
